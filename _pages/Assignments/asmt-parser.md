## Part 1: An LR(1) Calculator in Python

**You write:** every `TODO` in `python/calculator.py`, plus a hand trace in `notes.md`.
**You run:** the check after each step, from inside `python`.  `lexer.py` is complete.

Here is the grammar.  It is small enough that you can look at every state.

```text
0  S' -> E
1  E  -> E + T
2  E  -> E - T
3  E  -> T
4  T  -> T * F
5  T  -> T / F
6  T  -> F
7  F  -> ( E )
8  F  -> num
```

Precedence lives in the levels: an `E` is built from `T`s, and a `T` is built from `F`s, so `*` is reduced before `+`.  The rules are left-recursive, which an LR parser handles without trouble, so `8 - 3 - 2` means `(8 - 3) - 2`.

An LR parser keeps a stack and repeats one of two moves.  It *shifts* the next token onto the stack, or it *reduces* the top of the stack to a non-terminal when a right-hand side is complete.  The tables tell it which move to make, so most of this part builds those tables.

### Step 1.1: Trace a tiny grammar by hand

Trace this grammar on paper first, in `notes.md`.  Every function you write does what you do here.

```text
0  S' -> E
1  E  -> E + n
2  E  -> n
```

An **LR(1) item** is a production, a dot showing how much of it the parser has seen, and a lookahead: the token that must come next once the production is complete.  `[E -> E . + n, $]` means "I have seen an `E`, I expect `+ n`, and after that I expect `$`."

The closure rule says that if an item has the dot before a non-terminal `B`, as in `[A -> x . B y, a]`, the parser may be about to see a `B`, so it may also be at the start of any `B` production.  Add `[B -> . z, b]` for every `B -> z`, where `b` is any token that can come right after this `B`: whatever begins `y`, or `a` if `y` is empty.

### Step 1.3: FIRST sets

Closure needs to know which tokens can begin a non-terminal, because that is what can come next.  To know `FIRST(T)` you need `FIRST(T)`, since `T -> T * F`, so you cannot compute these in one sweep.  You start with empty sets and sweep until nothing changes.  That is a *fixed point*, and closure uses the same idea:

```text
first = an empty set for each non-terminal
repeat:
    for each production A -> X ... :
        add X to first[A] if X is a terminal, or everything in first[X] if it is not
until a whole sweep changes nothing
```

No production here is empty, so only the first symbol of a right-hand side matters.

```bash
python3 -c "from calculator import first_sets; f = first_sets(); print(sorted(f['F']), sorted(f['E']))"
```

> **You should see.** `['(', 'num'] ['(', 'num']`

### Step 1.4: Closure

Write the lookahead piece first.  Given an item `[A -> x . B y, a]`, `lookaheads(y, a, first)` returns the tokens that can follow `B`:

```text
if y is empty:                  {a}          what follows this production also follows B
if y starts with a terminal t:  {t}
otherwise:                      first[y[0]]
```

Now closure.  **One pass is not enough.**  Adding `[E -> . T, $]` puts a dot before `T`, which pulls in new productions.  Adding `[E -> . E + T, $]` then gives `E` a new lookahead, `+`, so every `E` item has to be added again with that lookahead.  So it is a fixed point again:

```text
closure(items):
    result = set(items)
    repeat:
        new = empty set
        for each item (p, dot, a) in result:
            if the symbol after the dot is a non-terminal B:
                for each b in lookaheads(what comes after B, a, first):
                    for each production q of B:
                        add (q, 0, b) to new
        if new adds nothing to result: return frozenset(result)
        result = result | new
```

Compute `first_sets()` once, because it never changes.  Do not add to `result` inside the loop that walks it, because Python raises a `RuntimeError` if a set changes size during iteration.  That is why the pseudocode collects into `new`.

```bash
python3 -c "from calculator import closure; print(len(closure({(0, 0, '\$')})))"
```

> **You should see.** `35`.  This is state 0.

> **If it fails.**  A much smaller count, with every lookahead `$`, means your loop makes a single pass, or `lookaheads` always returns `{a}`.  If it never finishes, your loop decides something changed even when `new` added nothing.

### Step 1.5: Goto

`goto(state, X)` answers: "if the parser is in this state and sees `X`, where does it go?"  Every item with the dot before `X` moves its dot past `X`, and the lookahead stays the same.  Any other item drops out.  Then close the result, since the dot may now sit before a non-terminal.  If no item can move, the result is an empty `frozenset`, which means there is no edge.

```text
goto(state, X):
    moved = { (p, dot + 1, a) for each (p, dot, a) in state whose symbol after the dot is X }
    return closure(moved)
```

**Why lookaheads matter.**  Follow `num` from two places, the top level and inside parentheses.  The production is the same, but the machine keeps two states, because it remembers the context.  In the first state below a `)` has no action, so an extra `)` fails right where the mistake is.

```bash
python3 -c "from calculator import *; i0 = closure({(0, 0, '\$')}); print(*sorted(show_item(i) for i in goto(i0, 'num'))); print(*sorted(show_item(i) for i in goto(goto(i0, '('), 'num'))); print(len(goto(i0, '+')))"
```

> **You should see.** The two states, and then `0`, because no item in state 0 has the dot before `+`.
>
> ```text
> [F -> num ., $] [F -> num ., *] [F -> num ., +] [F -> num ., -] [F -> num ., /]
> [F -> num ., )] [F -> num ., *] [F -> num ., +] [F -> num ., -] [F -> num ., /]
> 0
> ```

### Step 1.6: Build the states

The machine's states are every set of items reachable from state 0.  So start from state 0, try `goto` on every symbol, and treat each new result as a new state to explore.  Keep a dictionary from state to number, so that one lookup tells you whether a result is new.

```text
build_states():
    states = [ closure({(0, 0, "$")}) ]
    worklist = [ 0 ]
    while worklist is not empty:
        i = take the FRONT of worklist
        for X in SYMBOLS:
            g = goto(states[i], X)
            if g is empty: skip it
            if g is new: give it the next number, add it to states, and add that number to the BACK of worklist
            transitions[(i, X)] = the number of g
    return states, transitions
```

Use exactly this worklist order and `SYMBOLS`, so that everyone gets the same state numbers.

```bash
python3 -c "from calculator import *; s, t = build_states(); print(len(s), t[(0, 'E')], t[(0, 'num')], t[(0, '(')])"
```

> **You should see.** `30 1 4 5`

### Step 1.7: Build the tables

Read the tables straight off the states.  `action[i][terminal]` is `("s", j)` to shift and go to state `j`, `("r", p)` to reduce by production `p`, or `("acc",)` to accept.  `goto_table[i][nonterminal]` is a state number.  For every item `(p, dot, a)` in state `i`:

1. If the dot is before a terminal `t`, then `action[i][t]` is `("s", transitions[(i, t)])`.
2. If the dot is at the end and `p` is not 0, then `action[i][a]` is `("r", p)`.  Only on `a`: this is what the lookahead is for.
3. If the dot is at the end and `p` is 0, then `action[i]["$"]` is `("acc",)`.
4. If a cell already holds a *different* action, append `(i, token, old, new)` to `conflicts`, and leave the cell alone.  A table builder that overwrites hides an ambiguous grammar from you.

`goto_table` comes from every edge in `transitions` whose symbol is a non-terminal.

```bash
python3 -c "from calculator import *; s, t = build_states(); a, g, c = build_tables(s, t); print(c); print(sorted(a[t[(0, '(')]])); print(sorted(a[t[(0, 'num')]].items()))"
```

> **You should see.** No conflicts.  After `(` the parser can shift only what starts an expression.  After a `num` it reduces by production 8 on each lookahead:
>
> ```text
> []
> ['(', 'num']
> [('$', ('r', 8)), ('*', ('r', 8)), ('+', ('r', 8)), ('-', ('r', 8)), ('/', ('r', 8))]
> ```

### Step 1.8: Run the table, and compute as you reduce

The driver is short, because the table holds all the knowledge.  It keeps a stack of state numbers, which starts as `[0]`, and a stack of values, which starts empty.  A value stack is what lets it calculate: a token's value goes on when it is shifted, and a reduction replaces the values of its right-hand side with one answer.

```text
pos = 0
loop:
    entry = action[top of state stack][type of tokens[pos]]
    no entry:   raise ParseError(the token's type, its col)
    shift j:    push j and the token's value, and move to the next token
    reduce p:   pop len(rhs of p) from both stacks, keeping the popped values in order as v
                push reduce_value(p, v), then push goto_table[new top state][lhs of p]
    accept:     return the top of the value stack
```

Look up the GOTO from the state the pops *exposed*, not the state you were in.  That state remembers what the parser was doing before this right-hand side began.

`reduce_value` has productions 1, 3, and 8 done for you.  Fill in 2, 4, 5, 6, and 7 the same way.  Think about what `v` holds for each one: for `F -> ( E )`, `v` has three values, and the answer is the middle one.

Here is how the values move on `1 + 2 * 3`:

```text
shift 1, reduce F -> num, T -> F, E -> T      values: 1
shift +, shift 2, reduce F -> num, T -> F     values: 1 + 2
shift *, shift 3, reduce F -> num             values: 1 + 2 * 3
reduce T -> T * F                             values: 1 + 6
reduce E -> E + T                             values: 7
```

The `*` happens first because the table says to shift it while `T` is on top, and no code in your driver mentions precedence.

```bash
python3 calculator.py "1 + 2 * 3"
python3 calculator.py "(1 + 2) * 3"
python3 calculator.py "8 - 3 - 2"
python3 calculator.py "8 / 2 / 2"
python3 calculator.py "1 + ) 2"
```

> **You should see.** `7`, `9`, `3`, and `2.0`.  The last command ends in `calculator.ParseError: ParseError at col 5: unexpected )`.

> **If it fails.**
> - A `KeyError` from `goto_table`: you read the top state before you popped.
> - A `KeyError` on `action` instead of a `ParseError`: use `.get`, because an empty cell is how a syntax error shows up.
> - `5` for `8 - 3 - 2` or a string where a number belongs: check the order of `v`, and check that production 8 is what turns a token's text into a number.

## Part 3: Add Variable Assignment and Lookup

A variable needs two things: somewhere to keep its value, and grammar rules that use it.  The somewhere is a *symbol table*, which maps names to values.  Both versions use the same two grammar rules: a name in an expression looks up its value, and an assignment stores one.

Assignment goes in its own level, `A`, above `E`.  If you put `id = E` directly into `E`, the grammar has shift/reduce conflicts, because after `x = 1` the parser cannot tell whether a `+` continues the right side.  The new level settles it, and the rule refers to itself so that `a = b = 2` works.
