In this assignment you build the machine a parser generator would build for you.  You implement an LR(1) parser for one small grammar: your code computes the parse tables from the grammar, a driver runs those tables on a program's tokens, and the driver builds an abstract syntax tree (AST) as it goes.  The lexer is provided, so this assignment does not depend on your earlier work.


> **You should see.**
>
> ```text
> ['let', 'id', '=', 'num', '+', 'num', ';', '$']
> ```

Here is the grammar.  It has statements, arithmetic, and parentheses, and it is small enough that you can look at every state.

```text
 0  S'      -> program
 1  program -> program stmt
 2  program -> stmt
 3  stmt    -> let id = expr ;
 4  stmt    -> print expr ;
 5  expr    -> expr + term
 6  expr    -> expr - term
 7  expr    -> term
 8  term    -> term * factor
 9  term    -> factor
10  factor  -> ( expr )
11  factor  -> num
12  factor  -> id
```

Precedence lives in the levels: an `expr` is built from `term`s, and a `term` is built from `factor`s, so `*` ends up deeper in the tree than `+`.  The rules are left-recursive, which an LR parser handles without trouble, so `8 - 3 - 2` means `(8 - 3) - 2`.

An LR parser keeps a stack and repeats one of two moves.  It *shifts* the next token onto the stack, or it *reduces* the top of the stack to a non-terminal when a right-hand side is complete.  The tables tell it which move to make.  The rest of this assignment builds those tables.

Add `[B -> . z, b]` for every `B -> z`, where `b` is any token that can come right after this `B`: whatever begins `y`, or `a` if `y` is empty.

### Step 1.2: FIRST sets

Closure needs to know which tokens can begin a non-terminal, because that is what can come next.  `FIRST(factor)` is `( id num`.  `FIRST(term)` is the same, because a `term` starts with a `term` or a `factor`.

Notice the problem: to know `FIRST(term)` you need `FIRST(term)`, and `FIRST(expr)` depends on `FIRST(term)`.  So you cannot compute these in one sweep.  You start with empty sets and sweep until nothing changes.  That is a *fixed point*, and you will use the same idea in closure:

```text
first = an empty set for each non-terminal
repeat:
    for each production A -> X ... :
        add X to first[A] if X is a terminal, or everything in first[X] if it is not
until a whole sweep changes nothing
```

No production here is empty, so only the first symbol of a right-hand side matters.  `first[A] |= other` adds a whole set, and `other <= first[A]` asks whether it would add nothing.

```bash
python3 -c "from lr1 import first_sets; f = first_sets(); print(sorted(f['stmt']), sorted(f['program'])); print(sorted(f['factor']), sorted(f['expr']))"
```

> ['(', 'id', 'num'] ['(', 'id', 'num']
> ```

### Step 1.3: Closure

The closure rule from Part 0 has two pieces, so write the lookahead piece first.  Given an item `[A -> x . B y, a]`, `lookaheads(y, a, first)` returns the tokens that can follow `B`:

```text
if y is empty:          {a}                 nothing else is left in this production, so what follows it follows B
if y starts with a terminal t:  {t}
otherwise:              first[y[0]]
```

For example, take `[factor -> ( . expr ), +]`.  The non-terminal after the dot is `expr`, and `y` is `)`, so anything that closes in as an `expr` has the lookahead `)`.  The `+` is what comes after the whole factor, and it has nothing to do with the inside of these parentheses.

Now closure.  **One pass is not enough**, for two reasons you saw in Part 0.  Adding `[expr -> . term, ;]` puts a dot before `term`, which pulls in new productions.  Adding `[expr -> . expr + term, ;]` then gives `expr` a new lookahead, `+`, so every `expr` item has to be added again with that lookahead.  So it is a fixed point again:

```text
closure(items):
    result = set(items)
    repeat:
        new = empty set
        for each item (p, dot, a) in result:
            if the symbol after the dot is a non-terminal B:
                for each b in lookaheads(what comes after B, a, first):
                    for each production q of B:
                        add (q, 0, b) to new
        if new adds nothing to result: return frozenset(result)
        result = result | new
```

Compute `first_sets()` once, at the top of `closure` or in a module-level variable, because it never changes.  Do not add to `result` inside the loop that walks it: Python raises `RuntimeError: Set changed size during iteration`, which is why the pseudocode collects into `new`.

```bash
python3 -c "from lr1 import closure, show_item; i0 = closure({(0, 0, '\$')}); print(len(i0)); print(*sorted(show_item(i) for i in i0), sep='\n')"
```

> **You should see.** Thirteen items.  This is state 0.  Your statements have three lookaheads each, because a statement can be followed by `let`, by `print`, or by the end of the file:
>
> ```text
> 13
> [S' -> . program, $]
> [program -> . program stmt, $]
> [program -> . program stmt, let]
> [program -> . program stmt, print]
> [program -> . stmt, $]

> - Five items, all with `$`: `lookaheads` always returns `{a}`, so it ignores what comes after the non-terminal.
> - It never finishes: your loop decides something changed even when `new` added nothing.

### Step 1.4: Goto

`goto(state, X)` answers: "if the parser is in this state and sees `X`, where does it go?"  Every item with the dot before `X` moves its dot past `X`, and the lookahead stays the same.  Any other item cannot continue on `X`, so it drops out.  Then close the result, since the dot may now sit before a non-terminal.  If no item can move, return an empty `frozenset`, which means there is no edge.

```text
goto(state, X):
    moved = { (p, dot + 1, a) for each (p, dot, a) in state whose symbol after the dot is X }
    return closure(moved)
```

**Why lookaheads matter.**  Follow `num` from two places, the top level of a `print` and inside parentheses:

```text
print num .      gives   [factor -> num ., ;]  [factor -> num ., +]  [factor -> num ., -]  [factor -> num ., *]
print ( num .    gives   [factor -> num ., )]  [factor -> num ., +]  [factor -> num ., -]  [factor -> num ., *]
```

The production is the same, but the machine keeps two states, because it remembers the context.  In the first state a `)` has no action, so `print 1 ) ;` fails at the `)`, right where the mistake is.  A parser with no lookaheads on its items would have to reduce first and find out later.  In larger grammars this also removes conflicts that simpler tables cannot resolve.

```bash
python3 -c "from lr1 import *; i0 = closure({(0, 0, '\$')}); a = goto(goto(i0, 'print'), 'num'); b = goto(goto(goto(i0, 'print'), '('), 'num'); print(*sorted(show_item(i) for i in a)); print(*sorted(show_item(i) for i in b)); print(len(goto(i0, '+')))"
```

> **You should see.** The two states above, and then `0`, because no item in state 0 has the dot before `+`.
>
> ```text
> [factor -> num ., *] [factor -> num ., +] [factor -> num ., -] [factor -> num ., ;]
> [factor -> num ., )] [factor -> num ., *] [factor -> num ., +] [factor -> num ., -]
> 0
> ```

## Part 2: States, Tables, and the Driver

**You write:** `build_states`, `build_tables`, and `drive` in `lr1.py`.

### Step 2.1: Build the states

The machine's states are every set of items reachable from state 0.  So start from state 0, try `goto` on every symbol, and treat each new result as a new state to explore.  Keep a dictionary from state to number, so that one lookup tells you whether a result is new.  That only works because a state is a `frozenset`.

```text
build_states():
    states = [ closure({(0, 0, "$")}) ]
    worklist = [ 0 ]
    while worklist is not empty:
        i = take the FRONT of worklist
        for X in SYMBOLS:
            g = goto(states[i], X)
            if g is empty: skip it
            if g is new: give it the next number, add it to states, and add that number to the BACK of worklist
            transitions[(i, X)] = the number of g
    return states, transitions
```

Use exactly this worklist order and `SYMBOLS`, so that everyone gets the same state numbers.

```bash
python3 -c "from lr1 import *; s, t = build_states(); print(len(s), t[(0, 'print')], t[(0, 'let')], t[(0, 'program')]); print(sum(len(x) for x in s))"
```

### Step 2.2: Build the tables

Read the tables straight off the states.  `action[i][terminal]` is `("s", j)` to shift and go to state `j`, `("r", p)` to reduce by production `p`, or `("acc",)` to accept.  `goto_table[i][nonterminal]` is a state number.

For every item `(p, dot, a)` in state `i`:

1. If the dot is before a terminal `t`, then `action[i][t]` is `("s", transitions[(i, t)])`.
2. If the dot is at the end and `p` is not 0, then `action[i][a]` is `("r", p)`.  Only on `a`: this is what the lookahead is for.
3. If the dot is at the end and `p` is 0, then `action[i]["$"]` is `("acc",)`.
4. If a cell already holds a *different* action, append `(i, token, old, new)` to `conflicts`, and leave the cell alone.  A table builder that overwrites hides an ambiguous grammar from you.

`goto_table` comes from every edge in `transitions` whose symbol is a non-terminal.  `action.setdefault(i, {})` creates a row the first time you write to it.

```bash
python3 -c "from lr1 import *; s, t = build_states(); a, g, c = build_tables(s, t); print(c); i = t[(0, 'print')]; print(sorted(a[i])); print(sorted(a[t[(i, 'num')]].items()))"
```

> **You should see.** No conflicts.  After `print` the parser can shift only what starts an expression.  After a `num` it reduces by production 11 on each lookahead:
>
> ```text

> ['(', 'id', 'num']
> [('*', ('r', 11)), ('+', ('r', 11)), ('-', ('r', 11)), (';', ('r', 11))]
> ```

### Step 2.3: Run the table

The driver is short, because the table holds all the knowledge.  It keeps a stack of state numbers, which starts as `[0]`, and a stack of symbols, which starts empty:

```text
pos = 0
loop:
    entry = action[top of state stack][type of tokens[pos]]
    no entry:   raise ParseError(the token's type, its line, its col)
    shift j:    push the token's type and j, and move to the next token
    reduce p:   pop len(rhs of p) from both stacks; then push lhs of p and goto_table[new top state][lhs of p]
    accept:     return True
```

Look up the GOTO from the state the pops *exposed*, not the state you were in.  That state remembers what the parser was doing before this right-hand side began.  When `trace` is true, print one row before each move: the symbol stack joined by spaces, left-justified in 28 characters; `| `; the remaining token types joined by spaces, left-justified in 26; `| `; and then `shift`, `reduce` with `show_production(p)`, `accept`, or `error`.

```bash
python3 -c "from lr1 import *; s, t = build_states(); a, g, c = build_tables(s, t); drive(tokenize('print 1 + 2 * 3;'), a, g, trace=True)"
python3 -c "from lr1 import *; s, t = build_states(); a, g, c = build_tables(s, t); drive(tokenize('print 1 ) ;'), a, g)"
```

> **If it fails.**

## Part 3: Build the AST as You Parse

A reduction is the moment the parser knows it has a whole phrase, so that is when to build its node.  The driver gets a third stack, of *values*, kept in step with the other two.  A shift pushes the token itself.  A reduce pops one value per right-hand symbol, passes them to `build_node`, and pushes what it returns.  At `accept`, the top value is the whole tree.

Here is `2 * 3` as it reduces.  Each value is built from values that were already on the stack, so the tree grows from the bottom up:

```text
shift 2                     values: Token(2)
reduce factor -> num        values: Num(2)
reduce term -> factor       values: Num(2)                         nothing new, so the value passes through
shift *, shift 3            values: Num(2)  Token(*)  Token(3)
reduce factor -> num        values: Num(2)  Token(*)  Num(3)
reduce term -> term * factor  values: BinOp("*", Num(2), Num(3))   three values become one
```

### Step 3.1: One node per production

`build_node(p, kids)` returns the value of production `p`, where `kids` holds one value per right-hand symbol.  The skeleton has productions 5, 6, and 12 done.  Fill in the rest, one at a time:

```python
def build_node(p, kids):
    """Return the value of production p.  kids holds the value of each right-hand symbol, in order."""
    if p == 5 or p == 6:                 # expr -> expr + term, expr -> expr - term
        left, op, right = kids
        return BinOp(op.value, left, right, op.line, op.col)
    if p == 12:                          # factor -> id
        tok = kids[0]
        return Var(tok.value, tok.line, tok.col)
    # TODO: 8, term -> term * factor.  The same shape as 5.
    # TODO: 7 and 9, expr -> term and term -> factor.  Pass kids[0] through.  They exist only for precedence, so they build nothing.
    # TODO: 10, factor -> ( expr ).  Return the inner value, kids[1].  The tree's shape now holds the grouping, so no node is needed.
    # TODO: 11, factor -> num.  A Num of int(tok.value), with the token's line and col.
    # TODO: 3, stmt -> let id = expr ;.  A Let named by the id token's value, holding kids[3], with the let token's line.
    # TODO: 4, stmt -> print expr ;.  A Print of kids[1], with the print token's line.
    # TODO: 2, program -> stmt.  A Program holding a list of one statement.
    # TODO: 1, program -> program stmt.  Append the statement to the Program in kids[0], and return that Program.
    raise NotImplementedError(f"no node for production {p}")
```
